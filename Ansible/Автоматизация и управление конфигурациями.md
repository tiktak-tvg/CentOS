#### Так как базовая автоматизация и управление конфигурациями (Nginx, балансировка, роли, шаблоны, лимиты фаервола, системное время) полностью освоены и работают без ошибок, вы можете выбрать вектор дальнейшего развития проекта:
1. Автоматизация бэкапов по расписанию (Cron): Добавить в нашу роль задачу, которая настроит планировщик cron на удаленных серверах, чтобы сценарий бэкапа из second_playbook запускался автоматически каждую ночь.
2. Сбор метрик и мониторинг: Написать новую роль для автоматической установки легкого агента мониторинга (например, Prometheus Node Exporter) на обе ноды кластера.
3. Безопасность (Hardening): Создать роль для базовой защиты серверов (отключение входа по паролю для root, настройка SSH на нестандартный порт, установка утилиты Fail2Ban).

Давайте автоматизируем регулярное создание бэкапов с помощью планировщика Cron. Мы сделаем так, чтобы удаленные серверы каждую ночь автоматически упаковывали свои конфигурации и логи, а управляющий сервер centpca мог их собирать.

На этот раз вместо написания отдельного плейбука мы создадим новую роль backup. Это позволит закрепить навыки работы с ролями и переменными.

##### Шаг 1. Создание структуры для роли backup
Инициализируем новую роль в вашей рабочей директории:
```bash
cd /etc/ansible/roles
ansible-galaxy init backup --offline
```

##### Шаг 2. Описание задач роли (tasks/main.yml)
Мы настроим Cron-задачу, которая будет каждую ночь в 03:30 запускать скрипт архивации. Для этого в Ansible есть удобный встроенный модуль cron.

Запишем задачи в файл роли:
```bash
cat << 'EOF' > /etc/ansible/roles/backup/tasks/main.yml
---
# tasks file for backup
- name: Создание директории для хранения локальных бэкапов на сервере
  file:
    path: /var/backups/system
    state: directory
    mode: '0700'

- name: Создание bash-скрипта для упаковки архива
  copy:
    dest: /usr/local/bin/make_backup.sh
    mode: '0755'
    content: |
      #!/bin/bash
      HOST=$(hostname)
      DATE=$(date +%Y-%m-%d)
      TAR_NAME="/var/backups/system/backup-${HOST}-${DATE}.tar.gz"
      
      # Архивируем конфиги и логи, старые архивы старше 7 дней удаляем
      tar -czf "$TAR_NAME" /etc/nginx/ /var/log/messages
      find /var/backups/system/ -type f -mtime +7 -name "*.tar.gz" -exec rm -f {} \;

- name: Добавление задачи в планировщик Cron (каждую ночь в 03:30)
  cron:
    name: "Nightly system backup"
    minute: "30"
    hour: "03"
    job: "/usr/local/bin/make_backup.sh > /dev/null 2>&1"
    state: present
EOF
```
vШаг 3. Подключение роли в главный плейбук (site.yml)

Теперь расширим наш конфигурационный файл site.yml, чтобы к целевым серверам применялась не только роль веб-сервера, но и роль бэкапов:
```bash
cat << 'EOF' > /etc/ansible/site.yml
---
- name: Комплексная настройка веб-кластера и бэкапов
  hosts: servers
  become: yes
  vars:
    web_page_title: "Мой крутой кластер балансировки v2!"
  roles:
    - webserver
    - backup
...
EOF
```
##### Шаг 4. Запуск и применение конфигурации
Запустите обновленный плейбук:
```bash
ansible-playbook /etc/ansible/site.yml
```

##### Давайте реализуем ещё задачи:
1. Централизованный сбор: Создадим регулярный скрипт на управляющем сервере centpca, который будет автоматически забирать созданные ночные архивы с удаленных серверов к себе в архив.
2. Безопасность (Hardening): Защитим наши серверы: отключим вход по небезопасным паролям через SSH, оставив доступ строго по SSH-ключам, и отключим удаленный вход для пользователя root (для повышения безопасности).

##### Этап 1. Автоматический сбор бэкапов на centpca

Чтобы управляющий сервер раз в неделю (или каждую ночь после 03:30) забирал файлы, мы добавим Cron-задачу на саму машину centpca, которая будет запускать наш проверенный second_playbook.yml.

Выполните команду на centpca для добавления задачи в локальный cron (например, сбор будет запускаться в 04:00 утра):
```bash
(crontab -l 2>/dev/null; echo "00 04 * * * /usr/bin/ansible-playbook /etc/ansible/second_playbook.yml > /dev/null 2>&1") | crontab -
```
Теперь цепочка полностью замкнулась: в 03:30 ноды делают бэкап локально, а в 04:00 мастер-сервер стягивает их в папку /backups/.

##### Этап 2. Защита SSH (Hardening) через Ansible
Перейдем к безопасности. Мы напишем новую роль security, которая настроит конфигурационный файл демона SSH (/etc/ssh/sshd_config) на удаленных серверах.
##### 1. Инициализируем новую роль:
```bash
cd /etc/ansible/roles
ansible-galaxy init security --offline
```
##### 2. Пропишем задачи безопасности в tasks/main.yml роли security:
Мы будем использовать встроенный модуль lineinfile. Он умеет находить нужные строки в конфигурационных файлах и безопасно менять их значения.
```bash
cat << 'EOF' > /etc/ansible/roles/security/tasks/main.yml
---
# tasks file for security
- name: Отключение авторизации по паролям в SSH (разрешаем только ключи)
  lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?PasswordAuthentication'
    line: 'PasswordAuthentication no'
  notify: Перезапуск SSH

  # Внимание: Убедитесь, что вы скопировали свои SSH-ключи (через ssh-copy-id), 
  # иначе после этого вы потеряете доступ к серверам!
- name: Отключение прямого удаленного входа для root (опционально, для безопасности)
  lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?PermitRootLogin'
    line: 'PermitRootLogin without-password'
  notify: Перезапуск SSH
EOF
```
##### 3. Создадим обработчик (Handler) для перезапуска службы SSH:
В Ansible конфигурационные файлы не перезапускают службу сразу. Вместо этого используется секция handlers. Служба перезапустится только один раз в самом конце плейбука и только если в файле конфигурации были реальные изменения.
```bash
cat << 'EOF' > /etc/ansible/roles/security/handlers/main.yml
---
# handlers file for security
- name: Перезапуск SSH
  service:
    name: sshd
    state: restarted
EOF
```
##### Этап 3. Подключение роли безопасности в главный плейбук

Обновим наш site.yml, добавив туда третью роль:
```bash
cat << 'EOF' > /etc/ansible/site.yml
---
- name: Комплексная настройка веб-кластера, бэкапов и безопасности
  hosts: servers
  become: yes
  vars:
    web_page_title: "Мой крутой кластер балансировки v2!"
  roles:
    - webserver
    - backup
    - security
...
EOF
```
##### Этап 4. Запуск
Запустите полное развертывание системы:
```bash
ansible-playbook /etc/ansible/site.yml
```
Вы создали отказоустойчивый и безопасный микрокластер по всем канонам DevOps:
1. Балансировщик (centpca) — циклически распределяет входящие запросы 50/50 по алгоритму Round-Robin и отслеживает состояние нод (Health Checks).
2. Серверы веб-нод (10.1.100.12 и 10.1.100.14) — имеют статические IP-адреса, отдают уникальные страницы с помощью Jinja2-шаблонов, автоматически делают бэкапы каждую ночь по cron и закрыты для входа по стандартным паролям (доступ только по защищенным SSH-ключам).
3. Организация кода — вся логика переведена на профессиональную структуру ролей (webserver, backup, security), которой очень удобно управлять из одного короткого файла site.yml.
